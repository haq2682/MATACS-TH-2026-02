## 1. AI vs. rules
### Q1a. Which steps use AI, and which are plain code or rules?
- **AI (2 steps):**
  - Fact extraction: price, weeks, warranties, licence and insurance statements, install counts and team details as JSON, each with an evidence quote.
  - Team and approach check: fixed yes/no rubric items (named lead, crew stated, safety plan, monitoring plan), each with a quote. The AI does not produce the final number.
- **Code/rules:** loading criteria for the category, PDF text extraction, validation of AI output, injection phrase scan, mandatory pass/fail checks, missing-data check, weighted scoring formula, sorting, reason text.
- **Humans:** upload and category choice, review/override, final award.

### Q1b. Why was the line drawn there?
AI is good at understanding free-form language but weak at arithmetic, can vary between runs and can be manipulated by text inside a proposal. Code has none of those weaknesses. So AI never decides pass/fail, never calculates scores and never sets the rank.

## 2. Consistency and explainability
### Q2a. How are scores made repeatable and explainable?
- The AI runs at temperature 0 with a fixed JSON schema, and only returns facts.
- Sub-scores use fixed formulas: experience by install count, price and timeline relative to the best eligible bid, warranty by years, team by rubric items.
- Weights come from the admin's criteria version, not from the AI.

### Q2b. If the same proposals were ranked twice, would the result be the same?
Yes. Extracted facts are cached against the file hash, prompt version and model version. A second run reuses the cached facts, and the scoring code is deterministic, so the ranking is identical. A forced re-extraction could vary slightly, so it is compared against the cache and any difference is flagged.

### Q2c. How does a reviewer see why a proposal ranked where it did?
For each proposal the screen shows the score per criterion, its weight, the formula inputs and the evidence quote behind every extracted fact. The reason text is generated by code from these numbers, so it can never disagree with the score.

## 3. Human in the loop
### Q3a. Where does a person review, confirm or override? 
1. **Upload:** the reviewer selects the category.
2. **Review screen:** the reviewer sees the ranked list plus every FLAGGED and INELIGIBLE proposal with its reason.
3. **Override:** the reviewer can confirm a result, clear a flag, or change a status or rank. A written reason is required.
4. **Final award:** always a human decision. The tool never awards anything.

### Q3b. What gets logged for audit?
Per run: file hash, criteria version, prompt version, model name, raw AI output, validation results, every sub-score and total, flags raised, each human action (confirm/override), who did it, when, and why.

## 4. Changing criteria
### Q4a. What happens to proposals already scored when an admin edits criteria or weights?
Criteria are versioned. An edit creates a new version and never overwrites the old one. Each score stores the version it used. Existing scores are marked outdated, the ranking shows a warning, and a reviewer cannot finalize an award on outdated scores.
 
### Q4b. How are those proposals re-scored?
Re-scoring is cheap: stored facts are reused and only the formula is rerun. AI is called again only if the new criteria need a fact that was never extracted (for example a new criterion), and then only for that field. If a mandatory criterion changes, the pass/fail check reruns and a proposal's status may change.

### Q4c. What happens to earlier results and the record?
Past rankings stay viewable under their original criteria version, and each change is logged with the admin's name, so earlier decisions remain explainable.
 
## 5. Risks
### Q5. What could go wrong, and how does the design guard against it?
| Risk | Safeguard |
|---|---|
| **Wrong extraction** | Every fact needs an evidence quote. Code verifies the quote exists in the PDF text and that numbers parse. Failures are flagged. Scanned PDFs without text go to manual review. |
| **Made-up facts** | The prompt requires `null` when a fact is missing. Missing key data (such as a timeline in D) is FLAGGED without guessing. |
| **Manipulation / prompt injection** | Proposal text is treated as data. The AI reports hidden instructions in `injection_detected`, and code separately scans for phrases like "rank first" or "full marks". C contains such text, so it is FLAGGED for a human. Because AI never scores or ranks, even a missed injection cannot change the rank directly. |
| **Mandatory rules bypassed** | Pass/fail is done by code on extracted facts. A licence "to be confirmed later" (B) counts as not held, so B is INELIGIBLE with a reason. |
| **Bias** | The AI sees only criteria-related content and is told to ignore company size, brand or reputation. Scoring uses fixed formulas, and a human makes the final call. |
| **Cost** | One extraction call per proposal, cached. Scoring needs no AI call, so re-ranking and criteria changes do not trigger new calls. |
